# Development conventions (for AI assistants and humans)

Read README.md and docs/ARCHITECTURE.md first. This file is identical to CLAUDE.md; edit both together when making changes.

## Current focus: preparing for the first open-source release

For the near term, the focus is getting the repo ready to go public: code, built-in guides, docs, and assets are all maintained in this one place. UI details follow the `Theme` tokens in the code and the existing implementation — there's no separate design reference doc anymore; when something doesn't match the code, the code wins.

## Product principles

- Keep existing elements, order, behavior, shortcuts, and copy; visuals use the existing Theme semantic tokens.
- The one structural departure: the sidebar sits directly on the window background (no panel, no border, no shadow), and a note is a white plane flush against the window's top/right/bottom edges (no gutter, rounded corners, border, or shadow).

## Code

- **Don't run rustfmt.** The code is deliberately compact; write new code in the style of the surrounding code, including comment density.
- **The document engine lives in `crates/core` (`fdl_core`) and doesn't depend on GPUI.** The model, format, editing kernel, library, import, and Markdown export all live here, and can only reference modules within core; UI code lives in the root crate. See docs/ARCHITECTURE.md.
- **Document structure changes only go through `editor::Core`.** The order is: `checkpoint` → a Core method → `Editor::changed()`. When adding a new structural operation, also add a corresponding random operation in `fuzz_tests.rs`'s `step`.
- Only blocks where `BlockKind::nests()` is true, and containers (quote, callout, split, column), can have children. Code blocks have no styling and no inline objects.
- **DocxXML's written-out format must be stable.** If you change the read/write logic, `crates/core/tests/fixtures/all-blocks.xml` must still round-trip byte-for-byte. When adding a new block type, add its canonical form to this fixture.
- **Use `Theme::*` semantic tokens for color**, falling back to the `theme::craft` color scale (`c(craft::N300)`). Only write a hex value when it's a measured value, with the source noted. Use `theme::shadow_*` for shadows, and `ui::popover` / `ui::menu_row` for menu shells.
- **For new icons, check Nucleo first (UI Outline 18, the same set as existing icons)**; only draw your own if nothing suitable exists there. Self-drawn icons should have a comment at the top of the SVG noting "drawn by this project." When adding or removing icons, update the count and list in THIRD_PARTY.md accordingly: the Nucleo license allows up to 100 icons in an open-source project.
- If you change code under `vendor/`, update vendor/PATCHES.md accordingly.
- If you change the library's directory layout in a way that would make an old version misread it, bump `store::FORMAT`. New fields on Meta always get `#[serde(default)]`.

## Before committing

```sh
scripts/check.sh        # cargo test --release + clippy --all-targets with zero warnings
```

When you change the editing kernel, run more random seeds: `FDL_FUZZ_SEEDS=2000 cargo test --release random_edits`.

For a refactor that only moves code around without changing appearance, use `tools/harness/compare.py` to compare screenshots before and after — they must match exactly (see tools/harness/README.md).

To get an automatic check on every commit: `git config core.hooksPath scripts/hooks`.

When releasing a version, update the version number in both `Cargo.toml` files together. Don't create commits unless the user explicitly asks for one.

## User data (never touch this)

- Product name Quiet.md, binary `quiet_md`, default library at `~/Documents/Quiet.md`. That's the user's real data: never commit it into the repo, never delete or modify files inside it. Never touch other apps' processes or data; when killing a process, only match a binary actually built from this repo.
- The local preview build is `dist-preview/Quiet.md Preview.app` (named with "Preview" so it's not confused with the installed app), started or updated via `scripts/preview.sh`, and it also uses the default library. On first launch, `src/guides.rs` seeds the built-in "Getting Started" guide into an empty library; it never overwrites an existing library.
- `shared-mock/library` is generated by `python3 shared-mock/guides/build.py <empty-dir>` from `shared-mock/guides/src/*.xml`: regenerate it whenever the guides change, and confirm it round-trips with `FDL_ROUNDTRIP_DIR=<dir> cargo test --release library_round_trips -- --ignored`. Guides should only document features that are already implemented, and titles shouldn't have emoji icons.
- Screenshots in the guides are re-captured with `shared-mock/guides/shots/shots.sh` (a window will float in the middle of the screen for about a minute, without stealing focus); remember to re-capture them after changing a UI shown in a guide.
- Test libraries should always go in a temporary directory, specified via `QUIET_MD_HOME`.

## UI scripting (tools/harness)

See tools/harness/README.md for the rules; key points:

- Don't use the real system clipboard; only use `key cmd-v` after a `clip`.
- Don't use `activate` to steal focus.
- Don't click these:
  - "Show in Finder" in Settings › Library, or "Open in Finder" in the "…" menu on the home and folder pages;
  - Links and "Search the web";
  - Print;
  - Quick Look.
- Don't use the `open` command.
- Use `pick` to select files.

## Environment notes

- The shell is zsh: an unmatched glob errors out directly, so arguments like `--include=*.rs` need to be quoted.
- `grep` is actually ugrep.
- On macOS, `sed -i` needs to be written as `sed -i ''`.
- There's no `timeout` command.
